# LiveSH 项目报告

## 1. 项目名称

**LiveSH：面向上海居住选择的 WebGIS 可视化分析系统**

## 2. 项目摘要

随着城市规模扩大和居住成本上升，居民在选择居住区域时往往需要同时考虑房价、交通、医疗、购物、休闲等多种因素。单纯比较房价或单纯统计设施数量，都难以完整回答“哪里住得更划算，也更方便”这一现实问题。

LiveSH 以上海市为研究对象，综合二手房挂牌数据、POI 设施数据和街道/镇边界数据，构建了一个面向居住选择的 WebGIS 可视化分析系统。项目从**行政区、街道/镇、房源点周边**三个层次展开分析，依次完成基础聚合、稳健评分、房源点可达性、E2SFCA 风格供需可达性和 5/10/15 分钟生活圈评价，并通过地图、指标卡片、图表和街镇明细实现联动展示。

系统当前已处理：

- 房源数据：152,105 条
- POI 数据：602,168 条
- 行政区：16 个
- 街道/镇：207 个

项目最终形成了一个既能展示空间分布，又能解释评分来源的综合分析平台，是数据工程、空间分析和可视化设计的完整实践。

## 3. 研究背景与选题意义

### 3.1 背景

在大城市中，居住决策通常不是单一指标问题。价格较低的区域可能交通不便、设施不足；配套完善的区域又可能面临较高房价。因此，居民真实关心的是一个多目标权衡问题：

```text
在可接受的居住成本下，哪里能够提供更好的日常生活便利性？
```

上海作为超大城市，区域差异明显，既具有较强的案例代表性，也适合开展空间可视化和城市数据分析。

### 3.2 选题意义

本项目具有以下意义：

1. **现实意义**：帮助用户从“价格 + 配套 + 可达性”的综合视角理解居住选择。
2. **数据分析意义**：将房价、POI、边界数据等多源数据进行清洗、融合和建模。
3. **空间分析意义**：从行政区进一步下钻到街道/镇和房源点周边，避免只停留在粗粒度统计。
4. **可视化意义**：通过 WebGIS、统计图表和交互联动，把复杂指标转化为可理解的信息。

## 4. 项目目标

本项目希望回答以下问题：

1. 上海哪些区域房价压力较高？
2. 哪些区域拥有更丰富的生活设施与更好的服务可达性？
3. 哪些区域在考虑房价、设施、供需匹配和生活圈之后，具有更好的综合表现？
4. 区级结论进一步下钻到街道/镇后，是否依然成立？
5. 如何通过可视化方式，让用户理解“为什么某个区域得分更高”？

## 5. 数据来源与数据说明

### 5.1 数据类型

项目使用的数据主要包括三类：

| 数据类型 | 文件或目录 | 用途 |
| --- | --- | --- |
| 房源数据 | `data/sh_house_dataset_raw.parquet` | 计算房价、房源分布、可达性和居住需求 |
| POI 数据 | `data/sh_poi_raw/` | 计算设施结构、服务供给、生活圈和供需匹配 |
| 街镇边界 | `data/sh_street_boundary/shanghai_street_boundary.shp` | 将房源和 POI 匹配到街道/镇 |

### 5.2 POI 分类

系统使用的 POI 类别包括：

- 购物
- 医疗
- 交通
- 休闲娱乐
- 公司企业
- 住宅

其中，购物、交通、医疗、休闲娱乐和公司企业主要用于刻画服务供给；住宅 POI 主要用于构造需求代理点和支持供需分析。

## 6. 数据处理流程

项目后端通过 `backend/app/process_data.py` 完成数据入库和指标生成。整体流程如下：

1. 读取房源 parquet、POI shapefile 和街镇边界。
2. 删除关键字段缺失的数据。
3. 对房源 ID 和 POI 唯一标识进行去重。
4. 统一行政区命名，减少多源数据带来的名称不一致问题。
5. 过滤明显超出上海范围的异常经纬度。
6. 将房源和 POI 进一步匹配到街道/镇。
7. 同时维护 WGS84 与 GCJ-02 两套坐标。
8. 生成区级、街镇级聚合指标。
9. 计算房源点可达性、供需可达性和生活圈指标。
10. 写入数据库，并输出派生审计结果。

### 6.1 坐标处理

项目中使用了两套坐标体系：

- **WGS84**：用于原始空间分析和距离计算
- **GCJ-02**：用于高德地图前端展示

由于高德地图使用 GCJ-02，如果直接把 WGS84 坐标放到地图上，会出现偏移。因此系统在入库过程中保留原始坐标，同时生成 GCJ-02 坐标，确保地图展示与空间分析都能正确进行。

## 7. 指标体系与模型设计

### 7.1 基础聚合指标

系统首先在区级和街镇级生成以下基础指标：

- 平均挂牌单价
- 平均挂牌总价
- 房源数量
- 各类 POI 数量
- POI 总量
- 商圈活跃度

商圈活跃度公式为：

```text
business_activity =
  购物 × 0.35 +
  交通 × 0.25 +
  医疗 × 0.15 +
  休闲娱乐 × 0.15 +
  公司企业 × 0.10
```

### 7.2 早期基线模型

项目保留了一个便于解释的早期基线模型：

```text
livability_score = 标准化(商圈活跃度) - 标准化(平均房价)
```

该模型可以快速描述“便利性高、房价低”的区域，但也存在不足：

- 只使用总量，忽略设施结构差异
- 没有体现服务供给与房源需求之间的比例关系
- 不能反映房源点附近是否真正可达
- 对小样本街镇容易产生不稳定结果

因此，项目继续扩展出更稳健的多阶段模型。

### 7.3 稳健评分

为了减少“POI 总量高就等于宜居”的片面性，系统进一步引入：

- 各类服务的每房源供给强度
- POI 多样性
- 房价负担分
- 区域活力分

形成：

```text
livability_score_v2
```

这一分数比早期基线更适合作为综合评价的中间层。

### 7.4 房源点可达性

为了从“有多少设施”进一步走向“是否真的方便到达”，项目围绕每个房源点计算：

- 购物可达性
- 交通可达性
- 医疗可达性
- 休闲娱乐可达性
- 企业可达性
- 最近交通距离
- 最近医疗距离

通过距离衰减函数，让距离较近的设施贡献更高，距离较远的设施贡献更低。

### 7.5 E2SFCA 风格供需可达性

仅看设施数量还不能说明资源是否充足，因为同样数量的设施在不同人口或住宅密度下，服务压力可能完全不同。因此项目引入了 E2SFCA 风格的供需可达性思想：

1. 先估计设施面对的潜在需求规模
2. 再计算居民或房源点可获得的设施供给水平

由此得到：

- `e2sfca_access_score`
- `e2sfca_value_score`
- `sample_reliability_score`
- `calibrated_score`

其中 `sample_reliability_score` 用于对样本不足的空间单元进行降权，避免结果被极少量样本扭曲。

### 7.6 5/10/15 分钟生活圈

为了贴近居民日常生活体验，项目进一步构建生活圈评分体系：

| 时间尺度 | 主要含义 |
| --- | --- |
| 5 分钟 | 基础日常生活 |
| 10 分钟 | 较完整日常生活 |
| 15 分钟 | 更充分的城市资源 |

每个尺度都综合：

- 覆盖率
- 加权可达性
- 设施多样性

最终得到：

```text
life_circle_score
calibrated_score_life_circle
```

当前系统的默认地图着色、Top5 推荐和排行榜，都以 `calibrated_score_life_circle` 为主要依据。

## 8. 系统架构设计

### 8.1 总体架构

系统采用前后端分离结构：

```text
数据层
  ├── 房源数据
  ├── POI 数据
  └── 街镇边界
        ↓
数据处理层
  ├── 清洗
  ├── 坐标转换
  ├── 街镇匹配
  ├── 指标计算
  └── 入库
        ↓
服务层
  ├── FastAPI 接口
  ├── 区级指标
  ├── 街镇指标
  └── 地图边界代理
        ↓
展示层
  ├── React 页面
  ├── 高德地图
  ├── ECharts 图表
  └── AI 建议模块
```

### 8.2 技术选型

| 模块 | 技术 | 选择原因 |
| --- | --- | --- |
| 前端 | React + Vite + TypeScript | 开发效率高，组件化方便，适合复杂联动界面 |
| 可视化 | ECharts | 图表类型丰富，适合排名、散点、热力图、雷达图 |
| 地图 | 高德地图 JS API | 适合国内地图展示，边界和底图效果较好 |
| 后端 | FastAPI | 接口开发简洁，性能较好，适合数据服务 |
| 数据处理 | pandas、SciPy、pyproj、pyshp | 适合表格处理、空间计算和 shapefile 读取 |
| 数据库 | SQLite / PostgreSQL | SQLite 便于本地开发，PostgreSQL 便于后续扩展 |

## 9. 系统功能设计

### 9.1 首页与项目说明

首页用于解释项目主题、分析目标和评分逻辑，让用户在进入地图前先理解系统关注的问题。

### 9.2 区级 GIS 地图

地图支持查看：

- 校准评分
- 生活圈
- 房价
- POI 总量
- 商圈活跃度

用户可以通过切换主题观察不同指标在上海空间上的分布差异。

### 9.3 推荐区域 Top5

系统根据 `calibrated_score_life_circle` 给出默认推荐区，并过滤房源样本数量过少的区域，使推荐结果更稳健。

当前 Top5 区域为：

| 排名 | 区域 | 平均房价（元/㎡） | 校准评分 |
| --- | --- | ---: | ---: |
| 1 | 黄浦 | 106042.6 | 0.513 |
| 2 | 虹口 | 72676.8 | 0.327 |
| 3 | 崇明 | 17709.5 | 0.319 |
| 4 | 静安 | 77659.8 | 0.275 |
| 5 | 长宁 | 74255.7 | 0.264 |

需要注意的是，该排名是基于当前模型、当前数据和当前权重得到的结果，不代表绝对意义上的“最佳居住区”，而是一个用于课程分析和比较的综合评价结果。

### 9.4 区域详情

区域详情展示：

- 房价
- 房源数量
- POI 数量
- 活跃度
- 校准评分
- 供需可达性
- 样本可信度

这样用户不仅能知道“谁排得高”，还可以理解“高在哪里”。

### 9.5 街道/镇精细分析

街镇模块支持：

- 按行政区筛选
- 模糊搜索
- 查看街镇排名
- 查看生活圈、覆盖率、最近交通和最近医疗距离等指标

这一模块解决了只看行政区平均值过于粗略的问题。

### 9.6 可视化分析模块

系统共设计四类图表模块：

1. 城市概览
2. 设施结构
3. 关系洞察
4. 评分模型

主要图表包括：

- 房价 Top10 柱状图
- POI 类别占比图
- 校准评分排名图
- 房价与活跃度象限图
- 相关性热力图
- 雷达图
- 评分分布图

### 9.7 AI 居住建议模块

当前系统已经完成 AI 建议的前后端链路设计：

- 前端提供 AI 建议展示区域
- 后端提供 `/api/ai/advice` 接口
- 后端可根据当前区域指标构造 prompt

目前该模块仍返回规则生成的占位文本，后续可以接入真实大模型服务，生成更自然的居住建议说明。

## 10. 交互设计

系统的交互设计强调“围绕同一个区域，多角度观察”：

1. 点击地图行政区，更新当前选中区域。
2. 点击推荐卡片，更新地图和详情。
3. 点击图表中的区域项，同步联动地图与面板。
4. 切换行政区后，街镇模块自动跟随筛选。
5. AI 建议模块随当前区域自动刷新。

这种联动方式可以减少用户在多个模块之间切换时的认知成本。

## 11. 项目亮点

### 11.1 多层空间分析

项目不是只停留在行政区平均值，而是下钻到街道/镇和房源点周边，分析层次更完整。

### 11.2 从数量统计走向供需与可达性

项目没有把“POI 多”简单等同于“更宜居”，而是进一步考虑设施距离、供需匹配和生活圈覆盖。

### 11.3 评分链路较完整

系统保留了从基线分到稳健分、可达性分、供需可达性分、生活圈校准分的多阶段结果，便于比较和解释。

### 11.4 可视化表达完整

地图、图表、详情和街镇模块相互联动，使系统不仅能给出结果，也能解释结果。

### 11.5 可扩展性较好

后端接口、数据库模型、前端类型和 AI 模块都已经拆分清楚，方便后续继续扩展。

## 12. 存在的不足

虽然项目已经实现了较完整的分析流程，但仍存在以下局限：

1. **生活圈仍基于近似距离**：当前主要依据空间距离和衰减函数，尚未接入真实路网步行时间。
2. **权重仍具有主观性**：不同人群对购物、交通、医疗等的偏好不同，当前权重并非个性化。
3. **房价使用挂牌数据**：挂牌价并不等同于最终成交价。
4. **供需代理仍较简化**：住宅 POI 和房源点只能近似代表居住需求，尚不能完全替代真实人口数据。
5. **AI 模块尚未接入真实模型**：目前只是占位实现。

## 13. 后续改进方向

未来可以从以下方向继续完善：

- 引入真实道路网络和步行时间，提升生活圈精度
- 引入人口、就业、学区、通勤等更多城市变量
- 增加用户预算和偏好输入，支持个性化推荐
- 支持街镇级图表下钻和空间聚类分析
- 接入真实大模型，生成更自然的解释和推荐语句
- 尝试使用 PostgreSQL + PostGIS，进一步增强空间查询能力

## 14. 项目总结

LiveSH 围绕“上海哪里住得更划算，也更方便”这一问题，完成了从数据清洗、空间匹配、指标建模到前后端可视化展示的完整流程。项目不仅实现了行政区层面的城市比较，还进一步扩展到街道/镇和房源点周边分析；不仅比较设施数量，也纳入可达性、供需关系和生活圈覆盖；不仅输出评分结果，也通过地图和图表解释评分来源。

从课程实践角度看，本项目综合运用了数据工程、空间分析、指标建模、前后端开发和可视化表达，较好地体现了大数据分析与可视化课程的综合应用能力。
