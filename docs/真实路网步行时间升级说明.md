# 真实路网步行时间升级方案大纲

## 1. 背景与目标

### 1.1 当前问题

当前 LiveSH 的可达性、E2SFCA 和 5/10/15 分钟生活圈指标主要基于房源点与 POI 点之间的投影平面距离计算。

现有方法优点是计算快、覆盖全量房源、结果稳定；但它没有考虑真实道路网络、小区出入口、河流铁路阻隔、过街设施、道路绕行等因素，因此会把部分“直线近但步行不方便”的设施高估。

### 1.2 升级目标

引入高德 Web 服务 API 的真实步行路线结果，用真实步行时间替代平面距离近似，提升生活圈和设施可达性指标的解释力。

考虑高德 API 日调用限制，本轮升级不直接覆盖上海全部街镇，而是采用分阶段验证：

```text
测试版本：仅调查杨浦区五角场街道
正式试算版本：调查杨浦区全部 12 个街镇
```

本次升级优先替换街镇级生活圈相关指标：

```text
life_circle_5min_score
life_circle_10min_score
life_circle_15min_score
life_circle_score
life_circle_5min_coverage
life_circle_10min_coverage
life_circle_15min_coverage
calibrated_score_life_circle
```

后续可进一步扩展到：

```text
shopping_access
traffic_access
healthcare_access
recreation_access
company_access
access_score
nearest_traffic_distance
nearest_healthcare_distance
e2sfca_access_score
```

## 2. 当前方法梳理

### 2.1 当前生活圈计算方式

当前生活圈使用固定空间半径近似步行分钟圈：

```text
5分钟生活圈：320m
10分钟生活圈：640m
15分钟生活圈：960m
```

对应代码中的距离衰减参数：

```text
5分钟生活圈：beta = 160m
10分钟生活圈：beta = 320m
15分钟生活圈：beta = 480m
```

核心公式：

```text
access = exp(-distance_m / beta_m)
```

### 2.2 当前街镇级指标生成方式

当前流程是：

```text
全量房源点
  -> 基于平面距离计算每套房的生活圈特征
  -> 按 district / street 聚合为街镇级均值
  -> 参与 calibrated_score_life_circle 计算
```

### 2.3 当前方法的局限

- 平面距离不等于真实步行距离或步行时间。
- 河流、铁路、高架、封闭小区、大型街坊会造成可达性高估。
- 5 分钟生活圈最容易被空间距离近似误导。
- POI 点位存在但入口不可达时，当前模型仍可能计入覆盖。

## 3. 升级后的总体路线

### 3.1 核心思路

升级后不再对全量房源逐点调用路线 API，而是按街镇抽样，用少量真实路线结果估计街镇级步行生活圈表现。

流程如下：

```text
每个街镇先按 `gcj02_lng + gcj02_lat` 去重，再随机抽样代表房源坐标点
  -> 每套房面向 21 类生活 POI 各匹配 2 个代表 POI
  -> 调用高德步行路线 API 获取 walk_minutes / walk_distance_m
  -> 形成 抽样房源 × POI 类别 的步行时间矩阵
  -> 重算 coverage / access / diversity / life_circle_score
  -> 按街镇聚合
  -> 替换街镇级生活圈指标
```

### 3.2 API 调用控制规则

每个街镇最多：

```text
6 套房 × 21 类 POI × 每类 2 个 POI = 252 组路线样本
```

如果一个街镇没有足够目标数量的唯一房源坐标点：

```text
抽取 min(目标房源数, unique_gcj02_coord_count) 个房源坐标点
```

如果某类 POI 搜索不到：

```text
该类别 route_status = missing_poi
该类别不贡献 access
coverage 视为未覆盖
```

本轮试算范围：

```text
杨浦区 12 个街镇：
12 × 252 = 3024 组路线样本上限

测试版本仅五角场街道：
1 × 252 = 252 组路线样本上限
```

说明：以上为路线调用上限。本轮 POI 候选全部来自本地 POI 数据，不调用高德 POI 搜索接口。

### 3.3 坐标约定

高德路线调用和本地 POI 候选坐标均使用 GCJ-02。

项目当前房源和 POI 均保留 GCJ-02 字段，因此高德 API 调用应优先使用：

```text
gcj02_lng
gcj02_lat
```

本轮只调用高德步行路线规划，不扩展骑行、公交或驾车路线。

### 4.2 10 分钟完善生活类

```text

```

### 4.3 15 分钟城市资源类

```text

```

### 4.4 POI 匹配原则

每套抽样房源对每个 POI 类别匹配 2 个代表 POI。

本轮固定使用本地 POI 数据，不调用高德周边搜索接口查 POI。

候选筛选策略：

```text
使用本地 POI 数据
按 poi_subtype 分组
对每套抽样房源，每个 poi_subtype 取空间距离最近的 2 个候选
仅对这些房源-POI 候选对调用高德步行路线
```

这样可以：

```text
避免高德 POI 搜索接口额外消耗 API 调用
保证 POI 口径与当前项目生活圈模型一致
让升级前后的差异主要来自“空间距离 vs 真实步行时间”
```

## 6. 用步行时间替代距离衰减

### 6.1 原公式

```text
access = exp(-distance_m / beta_m)
```

### 6.2 新公式

```text
access = exp(-walk_minutes / beta_minutes)
```

### 6.3 beta 取值

沿用当前项目“beta 等于阈值一半”的思想，但将单位从米换成分钟：

```text
5分钟生活圈：beta_minutes = 2.5
10分钟生活圈：beta_minutes = 5.0
15分钟生活圈：beta_minutes = 7.5
```

### 6.4 单类别贡献

```text
subtype_access = supply_weight × exp(-walk_minutes / beta_minutes)
```

如果同一类别有 2 个 POI 候选：

```text
先取 walk_minutes 较短的候选作为该类别代表
再计算 subtype_access
```

如果路线失败：

```text
subtype_access = 0
```

## 7. 生活圈指标重算方式

### 7.1 coverage

对每套抽样房源：

```text
5min_coverage =
  5分钟内可达的基础生活类数量 / 基础生活类总数

10min_coverage =
  10分钟内可达的基础生活类 + 完善生活类数量 / 对应类别总数

15min_coverage =
  15分钟内可达的全部 21 类数量 / 21
```

### 7.2 access

对每套抽样房源，在对应生活圈类别集合内累加时间衰减贡献：

```text
5min_access = sum(5分钟基础类 subtype_access)
10min_access = sum(5分钟基础类 + 10分钟完善类 subtype_access)
15min_access = sum(全部 21 类 subtype_access)
```

### 7.3 diversity

保留当前熵式多样性思路，但输入改为基于步行时间的 subtype_access。

### 7.4 house-level life circle score

沿用当前权重：

```text
5分钟：
score = 0.45 × coverage + 0.35 × access_norm + 0.20 × diversity

10分钟：
score = 0.40 × coverage + 0.40 × access_norm + 0.20 × diversity

15分钟：
score = 0.35 × coverage + 0.45 × access_norm + 0.20 × diversity
```

综合生活圈：

```text
life_circle_score =
  0.40 × life_circle_5min_score
  + 0.35 × life_circle_10min_score
  + 0.25 × life_circle_15min_score
```

## 8. 抽样结果回推街镇级指标

### 8.1 街镇聚合

对每个街镇，将 6 套抽样房源的生活圈结果求均值：

```text
street_life_circle_5min_score_route = mean(house_life_circle_5min_score)
street_life_circle_10min_score_route = mean(house_life_circle_10min_score)
street_life_circle_15min_score_route = mean(house_life_circle_15min_score)
street_life_circle_score_route = mean(house_life_circle_score)
```

coverage 同理按抽样房源均值聚合。

### 8.2 路线样本可信度

建议新增路线样本可信度：

```text
route_success_rate = route_success_count / route_expected_count

house_sample_rate = sample_house_count / min(目标房源数, unique_gcj02_coord_count)

route_sample_reliability_score =
  0.7 × route_success_rate
  + 0.3 × house_sample_rate
```

该字段仅作为提示字段和审计字段，用于识别 API 失败、POI 缺失或样本不足造成的不稳定结果。

本轮不把 `route_sample_reliability_score` 纳入最终推荐分公式。

### 8.3 与原 sample_reliability_score 的关系

当前 `sample_reliability_score` 主要反映街镇房源数量是否足够。

升级后建议保留它，并新增 `route_sample_reliability_score`：

```text
sample_reliability_score：房源总体样本可信度
route_sample_reliability_score：高德路线抽样可信度
```

本轮最终校准分仍只沿用原有 `sample_reliability_score`，路线可信度只在测试输出中展示。

## 9. 替换 calibrated_score_life_circle 的建议

### 9.1 当前公式

当前项目中大致为：

```text
base_score =
  0.30 × livability_score_v2
  + 0.30 × e2sfca_access_score
  + 0.30 × life_circle_score
  + 0.10 × value_score

calibrated_score_life_circle =
  base_score × sample_reliability_score × (0.6 + 0.4 × life_circle_score)
```

### 9.2 升级后第一阶段公式

建议仅替换 life_circle_score：

```text
base_score_route =
  0.30 × livability_score_v2
  + 0.30 × e2sfca_access_score
  + 0.30 × life_circle_score_route
  + 0.10 × value_score

calibrated_score_life_circle_route =
  base_score_route
  × sample_reliability_score
  × (0.6 + 0.4 × life_circle_score_route)
```

说明：

```text
route_sample_reliability_score 仅作为提示字段输出
不参与 calibrated_score_life_circle_route 计算
```

### 9.3 是否覆盖原字段

第一阶段建议不要立刻覆盖原字段，而是并行生成：

```text
life_circle_score
life_circle_score_route
calibrated_score_life_circle
calibrated_score_life_circle_route
```

审核结果稳定后，再决定是否将路线版字段作为正式默认推荐指标。

### 10.1 对比方式

升级前后的数据对比不做前端展示，只通过后端测试输出文件检查。

### 10.2 方法差异

| 维度 | 当前空间距离方法 | 升级后真实步行路线方法 |
| --- | --- | --- |
| 距离来源 | 投影平面距离 | 高德步行路线时间/距离 |
| 覆盖范围 | 全量房源 | 每街镇抽样房源 |
| 计算速度 | 快 | 慢，受 API 限额影响 |
| 稳定性 | 高，结果可重复 | 依赖抽样、API 成功率和本地 POI 候选完整性 |
| 路网真实性 | 弱 | 强 |
| 对阻隔敏感性 | 弱 | 强 |
| 解释性 | 技术上清晰，但生活直觉较弱 | 更符合用户对“走几分钟”的理解 |
| 成本 | 本地计算，无 API 成本 | 有 API 调用成本和并发风险 |

### 10.3 预期结果变化

升级后，以下区域可能得分下降：

- 靠近河流、铁路、高架、快速路但过街点少的街镇。
- 大型封闭小区、产业园、大学园区周边。
- POI 直线距离近，但真实步行需要绕行的区域。
- 本地 POI 密集但道路网络可达性差的区域。

以下区域可能得分上升或保持优势：

- 路网密集、街坊尺度小、步行路径直接的中心城区。
- 生活设施沿道路均匀分布的成熟居住街镇。
- 公交站、便利店、药店、超市等基础设施真实可步行到达的区域。

### 10.4 指标层面的差异

5 分钟生活圈变化最大：

```text
因为短距离下，路口、围墙、出入口、过街设施会显著影响结果。
```

10 分钟生活圈变化中等：

```text
部分绕行可以被时间阈值吸收，但路网阻隔仍会改变覆盖率。
```

15 分钟生活圈变化相对较小：

```text
大多数中等距离设施仍可能落在阈值内，但 access 衰减会体现远近差异。
```

## 11. API 调用与缓存策略

### 11.1 缓存目标

高德路线调用必须做成本地缓存。核心规则是：

```text
同一组 起点-终点-出行方式 如果已经成功或明确失败过
后续运行时直接读取缓存
不再次调用高德 API
```

这样可以：

```text
减少 API 消耗
避免重复扣额度
支持中断后 resume
方便后续反复生成测试输出和对比文件
```

### 11.2 缓存文件

建议新增缓存文件：

```text
data/cache/amap_walking_route_cache.jsonl
```

使用 JSONL 而不是单个大 JSON，原因是：

```text
每次 API 返回后可以立即追加写入
中途停止时已完成结果不会丢失
文件可逐行读取，适合断点续跑
```

缓存文件不应提交仓库。

### 11.3 缓存键

缓存键建议：

```text
origin_lng,origin_lat|destination_lng,destination_lat|walking
```

为避免浮点格式造成重复请求，坐标建议统一保留 6 位小数：

```text
121.473700,31.230400|121.475100,31.232000|walking
```

### 11.4 缓存内容

每行保存一条路线结果，示例：

```json
{
  "cache_key": "121.473700,31.230400|121.475100,31.232000|walking",
  "origin_lng": 121.4737,
  "origin_lat": 31.2304,
  "destination_lng": 121.4751,
  "destination_lat": 31.232,
  "mode": "walking",
  "duration_minutes": 4.6,
  "distance_meters": 380,
  "status": "ok",
  "source": "amap",
  "error_message": null,
  "created_at": "2026-05-30T12:00:00"
}
```

建议状态值：

```text
ok
no_candidate_poi
route_not_found
api_quota_exceeded
api_error
network_error
invalid_response
```

说明：

```text
ok：可直接复用
no_candidate_poi：本地 POI 数据中没有候选 POI，不需要请求路线
route_not_found：高德明确无路线，可复用
api_quota_exceeded：额度限制，通常不应长期视为有效失败
network_error：网络临时失败，后续 resume 可重试
invalid_response：响应格式异常，后续可重试或人工检查
```

### 11.5 调用逻辑

路线调用前先查缓存：

```text
1. 根据起点、终点、walking 生成 cache_key
2. 在 data/cache/amap_walking_route_cache.jsonl 中查找 cache_key
3. 若命中可复用状态，则直接返回缓存结果
4. 若未命中，才调用高德步行路线 API
5. 高德返回后立即追加写入缓存文件
6. 同步写入本次样本结果表，并标记 cache_hit
```

缓存命中时：

```text
api_call_count 不增加
route_source = amap_cache
cache_hit = true
```

实际调用高德时：

```text
api_call_count 增加
route_source = amap_api
cache_hit = false
```

### 11.6 并发控制

建议第一阶段串行或小并发执行：

```text
并发数：1-3
请求间隔：可配置
失败重试：最多 1-2 次
```

如果使用 JSONL 追加写入，第一版建议先串行执行，避免并发写文件带来重复行或写入冲突。后续如需并发，应增加文件锁或统一写入队列。

### 11.7 断点续跑

路线样本文件应支持断点续跑：

```text
已成功的 origin-destination 不重复请求
明确失败的 origin-destination 不重复请求
临时失败的 origin-destination 可按策略重试
再次运行时只补缺失项
```

推荐参数：

```bash
--resume
--dry-run
--max-api-calls 252
--qps 3
```

五角场测试版本可以先使用：

```bash
python -m app.sample_walking_routes --district 杨浦区 --street 五角场街道 --houses-per-street 6 --pois-per-subtype 2 --max-api-calls 252 --qps 3 --resume
```

## 12. 验收标准

### 12.1 数据完整性

- 每个街镇应有 `sample_house_count`。
- 每个街镇应有 `route_expected_count`。
- 每个街镇应有 `route_success_count` 和 `route_success_rate`。
- 每个街镇应生成路线版生活圈指标。

### 12.2 指标合理性

- 路线版生活圈分数范围应在 0-1。
- 路线成功率低的街镇不应被错误推高。
- 新旧评分差异应能通过真实路网阻隔或步行便利性解释。

### 12.3 对比报告

必须输出：

```text
新旧街镇评分相关性
平均分变化
排名变化 Top10
路线失败率统计
典型街镇案例
```
